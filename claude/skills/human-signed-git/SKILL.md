# Human-signed git

**Intent:** transparency and honesty. Every commit is AI-generated code that a human has read and signed off.
The git config can make the agent the author and the human the committer, so no AI attribution trailers are
needed. Never add `Co-authored-by`, `Generated by` or similar unless the repo's conventions explicitly
ask for them.

## Never (agents and sub-agents)
- `git commit` in any form (`--amend`, `--fixup`, …).
- Creating any commit object, even an unreferenced one: `git commit-tree`, `git stash` (it makes commits),
  `cherry-pick` without `--no-commit`, `merge` without `--no-commit`, or `rebase`.
- Moving HEAD without the human's explicit consent: `merge`, `rebase`, `reset`, `switch`/`checkout` of a branch,
  rewording. Creating a worktree on a fresh branch doesn't count (see `wt-desks`).
- Pushing to any branch other than your own, or force-pushing at all. Force-pushes after a rebase are the
  human's.

## Instead: stage + message
1. Stage exactly the files for the commit (`git add <paths>`). Check with `git diff --cached --stat`.
2. Write `commit-message.txt` at the worktree root (untracked, never staged), following the repo's commit
   conventions.
3. Hand off "READY-TO-SIGN". The human runs `git commit -F commit-message.txt` (signed) in the worktree.
4. Multi-commit: stage part 1 only, hand off "part 1 of N", and continue after the human signs.

After signing, the agent may `git push -u origin <own-branch>` and `gh pr create`. Treat `gh` as read-only
otherwise: no comments, reviews, labels, merges or edits.

## Simulating merges and rebases (no commits)
- Use `git merge-tree --write-tree --merge-base <old-base> <new-base> <branch-tip>` on EXISTING commits to see
  the result tree and the conflict list. It creates trees and blobs only, which is fine.
- Or, in a scratch detached worktree at `<new-base>`: `git apply --3way <your.patch>`, resolve, and stage.
- `git write-tree` on the staged result gives the expected tree hash for the rebase kit.

## Rebase kit (when a signed branch conflicts)
The agent prepares the kit; the human runs it (rebasing re-signs). Put it outside the repo (e.g.
`<job-tmp>/<id>-rebase/`), containing:
- `README.md` from `templates/rebase-readme.md`.
- `files/<repo-path>`: resolved copies of ONLY the conflicted files.
- `resolution-vs-<base>.diff` and gate logs, for review.

Rules for the README:
- **Guards are print-only.** Use `[ … ] && echo OK || echo STOP`. No `exit` and no `set -e`, because they kill
  the human's interactive shell.
- The first guard pins `origin/<base>` to the SHA the kit was prepared against. If the base moved, the kit
  must be redone, never copied blindly. (Real incident: a stale whole-file copy silently dropped a line
  that had landed on the base in the meantime.)
- Also pin `HEAD`, the branch name, and a clean worktree.
- After `git rebase` stops: guard the exact conflict set (`git diff --name-only --diff-filter=U`), copy the
  resolved files, stage, then guard `git write-tree` == the verified tree hash. That hash check is what makes
  the whole-file copy safe.
- Then `git rebase --continue`, check `git log -1 --format='%G? %s'` shows `G`, and
  `git push --force-with-lease`.
- Present it to the human in parts (guards first), copy-pasteable.

Whoever relays the kit (e.g. the Chief of Staff) should independently recompute the expected tree before
pinging the human: read the `merge-tree` result into a temporary `GIT_INDEX_FILE`, `update-index` the resolved
blobs in, then `write-tree`.

## Merge style
Ask the human once. A common preference: merge directly when there's no conflict; when there's a conflict,
rebase plus a force-push, done by the human.
